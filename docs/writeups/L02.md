## 1. Design

The Level 1 tasks keep running unchanged. Level 2 adds three tasks and the platform side.

| New task | Core | Period | Job |
|---|---|---|---|
| net | 0 | 100 ms | Wi-Fi state machine, retries, BOOT button |
| web | 0 | 5 ms | Local web server (status page, setup page) |
| cloud | 0 | idle 250 ms | NTP time, sends records over HTTPS |

The `web` and `cloud` tasks are not on the 5 s watchdog: a slow browser or a slow TLS handshake must not restart the board.

### How the setup page saves the details
1. With no saved network the board starts the access point `SmartClass-T17` with a random 8-character password, printed on the Serial Monitor. The light is blue.
2. The page at `192.168.4.1` lists nearby networks with signal bars, plus fields for the Wi-Fi password, Room ID and device token (a hidden network can be typed in).
3. The board checks the values (Room ID: 1–16 letters, digits, `-`, `_`) and saves them in flash (NVS): `ssid`, `pass`, `room`, `token`, `verified`. Only then does it connect.
4. After the first successful connection `verified=1`. The access point closes 10 s later.

### Reconnection strategy
| Situation | What the board does |
|---|---|
| Wi-Fi drops | Retries after 1, 2, 4, 8 s, then every 15 s. Never restarts. |
| Power cut | Reads the saved details and reconnects, no setup. |
| New details, wrong password or unreachable network | Back to setup mode within 15 s; the error is shown on the setup page. |
| Saved (verified) details, hotspot off | Keeps retrying forever, never falls back to setup. |
| BOOT button held 5 s, or `reset` | Clears the saved details, restarts in setup mode. |

### Local status page and mDNS
Stored in LittleFS and served at the board's IP address and at **`http://smartclass-t17.local`** (mDNS). It reads `/api/state` every second and shows: Room ID, local time (Asia/Dhaka), temperature, humidity, status, flame, door, last card UID, Wi-Fi signal, chip temperature, firmware version, connection state (`LIVE` when the server is reachable).

### Telemetry, time and `seq`
- Every 5 s a record with the fixed fields is built; each card tap becomes a `CARD_TAP` event at once; each start-up sends `BOOT` with the reset reason.
- `ts` is internet time (NTP). A record made before the clock is set waits in the outbox and is sent with its corrected time (never `ts=0`).
- `seq` comes from one counter kept in flash 100 ahead of the numbers issued, so it is never reused after a restart or power cut.
- If the server or Wi-Fi is down, up to 64 records wait on the board and are sent once the link returns.

### How replays are rejected
The database has a unique key on `(device_id, seq)` and the server inserts with `ON CONFLICT DO NOTHING`. A message whose `seq` is already stored inserts nothing, gets **HTTP 409**, and the row count does not change. The serial command `replay` resends the last record to show this.

### HTTPS with the server's certificate checked
The board connects with `WiFiClientSecure` and the root certificates ISRG Root X1 and X2 (Let's Encrypt) are compiled in; the server's chain (`coldchain.durnibar.tech` → Let's Encrypt YE1 → Root YE → ISRG Root X2 → ISRG Root X1) ends at them. The connection is refused if the certificate does not check out. Auth header: `Authorization: Bearer <device token>`.

### Offline / online on the platform
A background worker marks the device offline after **20 s** without a message (limit 30 s) and online again on the next message. After a backend restart the board's outbox is simply sent again.

### System architecture
See `docs/architecture.md`.

```
 ESP32-S3-CAM --HTTPS--> VPS (Caddy, Let's Encrypt) --> VM: nginx -> api -> postgres
                                                              ^         ^
                                                         worker (offline sweep)
                                              Dashboard <-- live WebSocket from api
 (later levels: AI services, weather service)
```

### No secrets in the repository
No password, key or token is in the firmware or the repository. The Wi-Fi password, Room ID and device token are typed on the setup page and stored in the board's flash. Server secrets live in `deploy/.env` on the VM (git-ignored). The device token is stored on the server only as a hash. The root certificates in the sketch are public.

## 4. Problems and fixes

| Problem | Fix |
|---|---|
| Setup timed out with correct details | The connect was issued while the network scan ran and was dropped, and only one attempt was made. Now it waits for the scan and retries inside the 15 s window. |
| Server refused every message with a new Room ID | The Room ID is chosen on the device; the server now moves the device to it. |
| Device marked offline after 30–35 s | The worker needed more than 30 s of silence and checked every 5 s. Now 20 s, checked every second. |
| TLS handshake could trigger the watchdog | `cloud` and `web` tasks are not on the task watchdog; HTTP timeouts are 4 s. |
| __ (anything found during testing) | __ |
